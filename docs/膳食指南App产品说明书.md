# 膳食指南 AI App - 产品说明书 (PRD)

## 1. 产品概述
**产品名称**：膳食指南 AI (Dietary Guidelines AI)
**产品定位**：一款基于《中国居民膳食指南（2022）》的智能化、对话式手机应用，提供膳食记录、营养信息与一般性膳食建议，不做疾病诊断。
**核心价值**：采用“多维记忆分析 → 智能规划与对话 → 实际记录 → 报告与记忆汇总”的动态闭环。系统将「营养数值计算」与「膳食结构建议」分开处理：AI 负责菜品识别、配方拆解、营养分析与解释，计算引擎负责数值核算，所有数值可追溯，避免用宏量营养素缺口代替膳食指南。

---

## 2. 核心业务流程 (User Flow)

用户在 App 中完整的一餐规划与记录路径如下（最核心的交互闭环）：

1. **触发规划**：用户点击“规划下一餐”按钮。
2. **多维度上下文分析 (三层分析法)**：
   * **当日基线 (计算与规划的基准)**：结合「每日营养目标 + 今日已记录的实际摄入 + 今日尚未记录的餐次」，判断当前缺口与后续餐次的规划方向。
     * 今日已摄入的数值是既成事实，任何推荐、历史数据或 AI 输出都不能改写它。
     * 营养缺口只用于表达“接下来该往哪个方向补”，**不等于必须补齐的配额**。
   * **近期分析 (调整优先级)**：提取最近 3～7 天的饮食记录，识别近期饮食结构（如：近三天蔬菜连续不达标），用于调整推荐顺序与结构倾向。
   * **长期分析 (调整优先级与解释口径)**：提取最近 30 天的周期统计或营养画像，识别长期习惯及目标一致性。
   * **边界说明**：近期与长期数据只影响“推荐什么、先推荐什么”，不改变今天已摄入的数值，也不直接决定菜单。
3. **AI 给出餐食选项**：系统同时参考（a）定量营养缺口（b）膳食结构建议（食物种类、搭配、推荐摄入区间）（c）检索到的膳食指南条目，给出这餐可以选择的具体菜名。
4. **对话与微调 (交互)**：用户可以对 AI 推荐的菜品进行替换（如：“把糖醋排骨换一个”）。AI 基于当前餐单、修改要求与本次替换需满足的营养约束重新推荐，结果由后端做最终校验。
5. **结束对话**：用户确定好要吃什么，或者不再需要建议时，主动结束此次对话。**（注意：规划结束 ≠ 实际已吃，此状态为“规划完成、等待记录”）**。
6. **实际饮食输入**：用户就餐完毕后，在记录界面输入这餐**实际吃了什么**、**量是多少**；提交时显式选择“补录”或“修正整餐”，并做幂等与版本校验。
7. **单次报告与多级汇总**：
   * 后端独立计算实际营养摄入（计算或估算，见 3.1）。
   * 生成单次分析报告。
   * 数据同步更新至当日及周/月统计。
8. **反哺未来**：更新后的统计与画像，作为下一次规划时的优先级参考。

## 3. 系统架构与核心规则 (System Rules)

为了确保系统的严谨性，必须建立明确的职责划分与状态流转机制。

### 3.1 营养计算引擎与 AI 菜品分析 (分析与数值分离)
AI 可以分析菜品营养价值，但分析结果必须可复核、可追溯，不能只给一段无法验证的文字。数值来源遵循以下顺序：

1. **优先由计算引擎核算**：命中食物营养数据库的标准食物，按重量换算。
2. **AI 拆解配方后核算**：复合菜品由 AI 识别原料、用量、用油量与烹饪方式，引擎按配方计算。
3. **AI 区间估算兜底**：无法匹配也无法拆解的菜品，由 AI 给出估算区间与置信度，明确标注，不作为精确值。

引擎的输出分为**两类结果，分别计算、分别使用**：

1. **定量营养指标**：能量、蛋白质、脂肪、碳水化合物、膳食纤维、钠、钙、铁、维生素等（以数据库支持范围为准），给出摄入值、目标值、差额与达成率。
2. **膳食结构建议**：食物种类数与搭配结构，如谷薯类、蔬菜、水果、畜禽鱼蛋、奶及奶制品、大豆及坚果、油盐的份量与推荐摄入区间（例：蔬菜 300～500 g/日、奶及奶制品 300 ml/日）。

推荐菜品时必须同时满足两类要求，**禁止只依据热量、蛋白质、脂肪、碳水化合物的差额推荐菜品**。

完整解析流程如下：
* **用户输入**：“200 克米饭和 150 克糖醋排骨”（也可上传照片）。
* **AI (菜品分析)**：识别食物与份量；对糖醋排骨这类复合菜品，拆解出原料、用油量、烹饪方式与成品份数，并输出置信度和分析依据。
* **后端 (计算引擎)**：
  * 匹配本地/云端的标准**食物营养数据库**（字段见 3.1.1）。
  * 按标准营养数据**计算或估算**营养摄入量：
    * 米饭、鸡蛋、牛奶等标准食物：由重量与标准数据换算，过程可复现。
    * 糖醋排骨等复杂菜品：按 AI 拆解的配方（经审核或复用已有配方）计算。
    * 无法拆解的菜品：使用 AI 区间估算。
  * 标注结果性质：`measured`（按标准数据换算）、`estimated`（按配方估算）、`ai_estimated`（AI 区间估算）。
  * 对照用户的每日营养目标与膳食结构建议进行校验。
* **AI (结果解释)**：后端将计算好的结构化数据发给 AI，由 AI 生成自然语言解释；AI 可解释分析依据，但不得改写引擎结果或把估算说成精确值。

> 计算过程可以确定，但输入数据（重量、配方）与复杂菜品的营养结果不一定精确，因此结果需标明性质、区间与置信度，并允许用户修正。

#### 3.1.1 食物营养数据库

| 字段 | 说明 |
| --- | --- |
| `food_id` | 主键 |
| `name` / `alias` | 食物名称与常见别名（用于自然语言匹配） |
| `category` | 谷薯类、蔬菜、水果、畜禽肉、水产、蛋类、奶类、大豆及坚果、油脂、调味品、复合菜品 |
| `nutrients_per_100g` | 每 100 克营养成分（能量、蛋白质、脂肪、碳水、膳食纤维、钠、钙、铁、维生素等） |
| `edible_ratio` | 可食部比例 |
| `source` | 数据来源与版本（如《中国食物成分表》标准版、膳食指南附录、其他权威来源） |
| `status` | 适用状态：`active` / `deprecated` / `pending_review` |
| `cooking_method` | 烹饪方式（蒸、煮、炒、炸等）及其对营养的影响 |
| `recipe` | 复合菜品配方：原料及用量、用油量、成品份数 |
| `unit_conversion` | 计量换算（碗、份、个 → 克） |

计算规则：
* 单一标准食物：按可食部、实际重量与标准数据换算。
* 复合菜品：按配方 + 烹饪方式 + 用油量估算，标注 `estimated`，并允许用户后期手动修正。
* 数据缺失或来源不明时，不输出精确值，只给区间或提示用户补充。

AI 推断的复合菜品配方先进入「配方候选（待审核）」，审核通过后转为正式配方；候选配方参与计算时结果标记 `estimated`，并保留 AI 的分析依据与置信度。

### 3.2 数据分层存储架构 (记忆的正确存放)
摒弃将所有“结论”塞入向量数据库的做法，采用结构化的分层存储：

1. **关系型数据库（事实来源）**：
   * 存储：食物营养数据库（见 3.1.1）与 AI 推断的配方候选。
   * 存储：餐次组、餐次记录与食物明细（含 `meal_group_id`、`meal_entry_id`、`revision`、`mode`、营养结果及 `value_type`）；统计只取当前有效版本，不累加历史版本。
   * 存储：规划会话与推荐餐单（含 `plan_session_id`，明确不计入实际摄入）。
   * 存储：规划校验规则与阈值版本（见 3.6）。
   * 存储：日报、周报、月报的结构化统计结果。
   * 存储：用户明确设置（每日营养目标、饮食偏好、忌口、过敏原）。
   * 存储：系统推断的饮食趋势（含状态、依据时间段、样本量，见 3.5）。
   * *用途：作为数值计算、历史回溯、报告生成的绝对事实来源。*
2. **Vector DB (向量数据库)**：
   * 存储：《中国居民膳食指南》知识库切片。
   * 存储：(可选) 历史对话语义记忆（如“用户上次为什么不想吃鱼”）。
   * *用途：为推荐与解释提供依据；不参与营养计算，也不作为事实数据来源。*

### 3.3 AI 对话状态管理 (State Machine)
为避免“规划数据”污染“实际摄入数据”，引入明确的业务状态机：

| 状态 | 含义 | 是否计入实际摄入 |
| --- | --- | --- |
| **待规划 (To Plan)** | 用户尚未开始本餐规划 | 否 |
| **规划中 (Planning)** | 规划会话进行中，AI 正在生成或调整菜品建议 | 否 |
| **规划完成待记录 (Planned, Awaiting Log)** | 用户已结束规划会话、记录页面已创建，等待实际提交 | 否 |
| **已记录 (Logged)** | 实际饮食已提交并保存 | 是 |
| **已分析 (Analyzed)** | 后端计算引擎完成营养分析，单餐报告及当日统计已更新 | 是 |

> 原「已结束规划」与「待记录」合并为「规划完成待记录」：前者表示规划会话结束，后者表示记录页面已创建，二者合并后状态定义更清晰，避免重叠。

**状态流转**：待规划 → 规划中 → 规划完成待记录 → 已记录 → 已分析（若事后修改，则从“已分析”触发重算并回到“已分析”）。

**异常与重复提交规则**：
1. **会话标识**：每次规划生成唯一 `plan_session_id`，推荐内容与该会话绑定，便于恢复与审计。
2. **中途退出恢复**：用户在规划中退出 App，再次进入时可恢复当前会话（保留推荐餐单与对话要点）；若用户选择重新开始，旧会话标记为 `abandoned`，不产生重复记录。
3. **餐次与版本**：餐次仅表示早餐、午餐、晚餐、加餐；同一餐次允许存在多个记录版本。餐次组以 `(用户, 日期, 餐次, 加餐实例序号)` 唯一，**加餐可在同一天出现多次**；每条餐次记录有唯一 `meal_entry_id` 与递增 `revision`。
4. **提交语义**：必须显式选择 `append`（补录，保留已有内容）或 `replace`（修正整餐，需携带 `base_revision`）；系统不做隐式覆盖。
5. **提交幂等**：客户端提交携带 `idempotency_key`，重复点击或网络重试返回同一结果，不新增版本。
6. **计算与统计幂等**：营养计算与周期统计更新按 `(meal_entry_id, 数据版本)` 幂等执行；统计只汇总当前有效版本（最新 `replace` + 其后所有 `append`），不得累加旧版本。
7. **并发控制**：同一餐次组的写入串行化；`base_revision` 已过期时返回冲突并回传当前版本，由客户端合并后再提交。
8. **历史修改**：修改已记录内容采用版本化追加，保留原始值与修改记录，并触发受影响日期的重算。

### 3.4 报告生成的时机与失效
报告不是完全由 AI 凭空生成的，而是数据与智能的结合：

1. **单餐报告（即时）**：每次提交（补录或修正）后，后端按该餐次组的当前有效版本重新计算，并更新当日统计，生成单餐报告。
2. **周期报告（按需 / 定时）**：周报、月报在用户打开页面时按需生成 AI 总结，并缓存已生成结果；也可由定时任务预生成。
3. **历史修改后的重算与失效**：用户补录或修改历史记录时，后端重新计算受影响的日期及周期统计，并将相关旧报告标记为失效（stale）或重新生成。
4. **数据与文字的边界**：报告中的数字一律来自后端计算结果；AI 的总结文字不能替代统计数字，也不得自行生成或修改数值。
5. **时区**：按用户所在时区的自然日切分统计。

### 3.5 长期营养画像的维护与纠错
长期画像分为两类，分别维护：

1. **用户明确设置（权威数据）**：每日营养目标、饮食偏好、忌口、过敏原。
   * 仅用户本人或明确确认的操作可以修改。
   * AI 对话不得自动覆盖用户设置。
2. **系统推断趋势（假设数据）**：由历史记录计算得出，如“近一周蔬菜摄入偏少”。必须带状态与依据：
   * `candidate`：样本不足或仅单周期出现，仅作参考。
   * `verified`：多个周期一致、样本量达标，可用于调整推荐优先级。
   * `invalidated`：被新数据推翻，保留记录但不再使用。

维护规则：
* 推断结论必须标注依据（时间段、样本餐次、指标偏差幅度）。
* 用户补录或修改历史数据后，系统重新计算相关指标，并复核原有结论是否仍然成立。
* 缺乏数据支持的推断不得作为长期事实保存。

### 3.6 规划校验规则（避免 AI 规划成为黑箱）
AI 生成的餐单不能直接展示给用户，必须由独立校验模块判定。规则与阈值配置化、版本化，校验结果以结构化数据返回，而不是一段错误文字。

| 校验项 | 规则 |
| --- | --- |
| 过敏原 | 硬性禁止：展开菜品与配方原料后比对，命中即失败，无例外 |
| 忌口 | 命中用户明确不接受的食物则失败或过滤 |
| 食物有效性 | 菜品必须存在于有效食物库，或能映射到有效配方 |
| 营养合理性 | 按「今日已摄入 + 剩余餐次 + 餐次分配权重」计算本餐合理范围，**不要求每餐达到每日目标** |
| 膳食结构 | 检查食物组构成，避免只满足能量却缺少蔬菜等食物 |
| 用户替换要求 | 先把自然语言要求转成结构化约束（如“素菜”“不辣”），再逐条确定性校验 |
| 重复菜品 | 同一餐内不得重复同一菜品 |
| 医疗边界 | 不做疾病判断或诊断 |

**本餐合理范围**

```
剩余目标     = max(每日目标 − 今日已摄入, 0)
剩余餐次权重 = Σ 今日未记录餐次的权重（含当前餐）
本餐期望     = 剩余目标 × 当前餐权重 / 剩余餐次权重
允许区间     = 本餐期望 × [1 − tolerance, 1 + tolerance]
```

* 默认餐次权重：早餐 0.25、午餐 0.35、晚餐 0.30、加餐 0.10，可按用户习惯调整。
* 默认 `tolerance` 为 20%；蛋白质只设下限，钠与脂肪设上限。
* 若今日已超出每日目标，转为“不显著超出 + 结构优先”，不再按补差计算。

**校验结果结构**：`passed`、`failed_rules`（含规则编号、涉及菜品、期望值与实际值）、`warnings`、`computed_ranges`、`rule_version`。

**处置方式**：硬性失败不展示给用户，直接把失败项交给 AI 定向重生成（最多 2 次），仍失败则由规则引擎从食物库兜底；软性失败展示为警告，由用户确认。每次规划的缺口快照、推荐理由、指南引用与校验结果一并保存，用户可查看“为什么推荐这道菜”。

**医疗边界**：产品只提供膳食记录、营养信息与一般性膳食建议，不判断用户是否患有某种疾病，也不根据少量记录得出疾病结论；涉及疾病或治疗问题时，提示咨询医生或注册营养师。

## 4. Token 优化策略 (必要上下文，不做无依据省略)
摒弃盲目输入大量历史数据的做法，做到“只向模型提供完成当前任务所需的信息”：

1. **规划上下文**：每日营养目标 + 今日已摄入汇总（定量指标与膳食结构达成情况）+ 尚未记录的餐次 + 近期结构化趋势（如连续三天缺蛋白）+ 长期画像摘要 + 忌口/过敏原/偏好。**不发送原始流水账**。
2. **追问/换菜上下文**：当前推荐餐单 + 修改要求 + 本次替换需满足的营养约束（定量目标与膳食结构，如“需补足蔬菜且蛋白质不低于 X”）+ 不可推荐项（过敏原、忌口、已被用户否决的菜品）+ 饮食偏好 + 上一轮校验失败项。缺少营养约束会导致换菜不成立。
3. **结构化校验闭环**：AI 返回的菜单必须经 3.6 的校验模块判定；失败时把 `failed_rules`（规则编号、涉及菜品、期望值与实际值）回传 AI 定向重生成，最多 2 次，仍失败由规则引擎兜底。不能只回传一段错误文本，也不能完全依赖 AI 自行判断。
4. **RAG 约束**：先检索指南，再精选相关条目交给 AI，严禁把整本指南放入 Prompt。检索到的指南内容用于支持推荐与解释，**不能代替营养计算引擎**。
