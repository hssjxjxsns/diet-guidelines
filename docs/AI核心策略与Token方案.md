# AI 核心策略与 Token 节约方案

在构建以 AI 为核心的膳食指南 App 时，如果每次都将用户的完整饮食记录和膳食指南全文发送给大模型，会导致 Token 消耗巨大、响应缓慢，甚至超出模型的上下文限制。

为了解决这个问题，我们设计了以下策略：

## 1. 知识库检索增强 (RAG) - 解决专业性与 Token 消耗
* **问题**：《中国居民膳食指南》内容庞大，直接放入系统 Prompt 会消耗大量 Token。
* **方案**：
  1. 将膳食指南的各个章节、核心准则切分为小的文本块 (Chunks)。
  2. 使用嵌入模型 (Embedding Model) 将文本块转化为向量，存入向量数据库 (如 Supabase pgvector)。
  3. 当用户提问（例如：“高血压患者怎么吃”）或系统生成餐单时，先在向量库中检索最相关的 Top-K 条指南。
  4. 只将检索到的**相关指南**作为上下文放入 Prompt 中。
* **定位**：检索结果只用于支持推荐与文字解释，不参与也不替代营养计算。营养数值由计算引擎核算；AI 可拆解菜品配方并给出区间估算，但必须标注依据、置信度与 `ai_estimated`。

## 2. 周期性营养画像 (Summarized Profile) - 解决长期记忆 Token 消耗
* **问题**：如果用户使用 App 一年，积累了上千条饮食记录，直接让 AI 根据这些记录给出建议是不现实的。
* **方案**：
  1. **短期记忆 (最近 3-7 天)**：读取结构化统计结果（每日定量指标与膳食结构达成情况），用于精准的短期调整。
  2. **长期记忆 (营养画像)**：利用定时任务 (Cron Job) 或后端计算，每周/每月根据统计数据生成，且必须分成两类分别维护。
* **画像分为两类**：
  1. **用户明确设置 (权威数据)**：每日营养目标、饮食偏好、忌口、过敏原。只有用户本人或明确确认的操作可以修改，AI 对话不得自动覆盖。
  2. **系统推断趋势 (假设数据)**：由历史记录统计得出，必须携带状态与依据，只有 `verified` 的结论才进入 Prompt：
     * `candidate`：样本不足或仅单周期出现，仅作参考。
     * `verified`：多个周期一致、样本量达标，可用于调整推荐优先级。
     * `invalidated`：被新数据推翻，保留记录但不再使用。
* **营养画像数据结构示例**：
  ```json
  {
    "user_id": "u_1001",
    "explicit": {
      "daily_targets": { "calories": 2000, "protein_g": 75 },
      "dietary_structure": { "vegetables_g": [300, 500], "dairy_ml": 300 },
      "preferences": ["清淡"],
      "allergens": ["花生"],
      "avoid": ["香菜"]
    },
    "inferred": [
      {
        "conclusion": "蔬菜摄入偏低",
        "metric": "vegetables_g",
        "status": "candidate",
        "evidence": {
          "period": "2026-10-18 to 2026-10-24",
          "sample_meals": 12,
          "avg_gap_g": -120
        }
      }
    ]
  }
  ```
* **更新与纠错机制**：
  * 每次记录提交后重算当日与当期统计；用户补录或修改历史记录时，重新计算受影响日期与周期，并复核原有结论是否仍然成立。
  * 推断结论需达到样本量与周期一致性要求，才能由 `candidate` 转为 `verified`；被新数据推翻则转为 `invalidated`，不再进入 Prompt。
  * 不能因为某次 AI 对话就把缺乏数据支持的推断当作事实长期保存，也不能用推断结果覆盖用户的明确设置。
* **工作流**：当用户询问“根据我过去半年的情况给我建议”时，系统只提取过去 6 个月的画像对象（明确设置 + 已验证趋势）发给 AI，而不是过去 180 天的具体三餐流水。这能将 Token 消耗降低 95% 以上。

## 3. 结构化输出与缓存
* **方案**：要求 AI 始终以 JSON 格式输出餐单和建议。对于通用的食谱组合，可以在数据库中建立缓存。如果用户请求的条件与缓存匹配，则直接返回，避免重复调用大模型。

## 4. 必要上下文的最小充分集
节省 Token 不等于省略关键约束。以下信息在对应场景中不可裁剪：
1. **规划时**：每日营养目标、今日已摄入汇总、尚未记录的餐次、近期结构化趋势、长期画像摘要、忌口/过敏原/偏好；不发送原始流水账。
2. **换菜时**：当前推荐餐单 + 修改要求 + 本次替换需满足的营养约束（定量指标与膳食结构）+ 不可推荐项（过敏原、忌口、用户已否决的菜品）+ 偏好。缺少营养约束时，替换结果可能满足口味却破坏整餐结构。
3. **结构化校验闭环**：AI 返回的菜单必须经校验模块判定（过敏原、忌口、食物有效性、动态营养范围、膳食结构、替换要求）；失败时回传 `failed_rules`（规则编号、涉及菜品、期望/实际值）定向重生成，最多 2 次，仍失败由规则引擎兜底，不能完全依赖 AI 自行判断。

## 5. 模型策略
* 对话、菜品分析（含照片）、单餐/周期总结统一使用智谱 `glm-5.3-flash`，避免多模型切换带来的口径不一致。
* 指南向量化使用 `embedding-3`，固定 1024 维（适配 pgvector HNSW）。
* AI 不承担疾病诊断；涉及疾病或治疗的问题只输出一般膳食建议并提示就医。
* 若后续引入更强模型，仅用于长报告总结；其输出仍受统计数字与校验规则约束。
